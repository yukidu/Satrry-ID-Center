# Starry Battery｜中央規則新增／修改 SOP（開發與維運）
日期：2026-10-24（台灣時間）

## 唯一權威
- 業務需求以 M06 正式 Google 文件為唯一權威。M06-A 是給非工程師的查詢摘要。
- 本倉庫 rules-catalog.json 是程式變更索引；不能自行凌駕 M06。
- 無法清楚判定的新規則一律狀態 pending / disabled，不能自行啟用。

## AI 必須遵守的主動專業審查
每次收到新想法，先辨識使用者目標，主動指出更安全／穩定／標準化／低成本的作法、可能衝突、影響哪款 App，以及哪些工作必須手動授權。不可只按字面無條件執行高風險功能。與已確認規格衝突時，更新 M06 決議但保留歷史。

## 安全開發流程
1. 讀最新版 00、M06、M04、M06-A、M09、99 及最新 GitHub main/PR SHA、Cloudflare 真實綁定。
2. 從 M06 對照『新增、修改、刪除』，與既有規則去重。列出受影響端點、身份 scope、schema CHECK/索引、原子性、帳本與退款規則。
3. 若是既有可配置參數，走受授權且有版本／稽核的設定機制；全新未支援的功能必須修 Gateway、private Engine、D1、API Contract 和測試；不可將安全檢查做成任意關閉的選項。
4. 所有 App 透過受保護中央 API，不得直接碰 Battery D1。跨 App API 需版本策略與向後相容；若要 App 新增欄位／UI，提供逐 App 升級需求。
5. 在隔離 D1 完成 Schema/資料升級演練、真實交易與併發 E2E、過期／逾時／取消全額退款、冪等、權限、濫用防護，CI 與安全掃描通過。
6. 建 branch→PR→安全 Preview→使用者／有權者驗收→merge main→正式 Worker/D1 部署→Production 健康與資料一致性驗證，準備 rollback；沒有足夠證據絕不宣稱正式上線。
7. 同步更新 rules-catalog.json、M06-A 總覽、M06 權威規格、M04 API 契約、M09 工程紀錄、99 交接摘要。記錄更新時間、PR/commit、已驗收與未驗收清單。
8. 將來要『直接編輯 M06 就即時觸發同步』，須另行建立經授權的 Google Drive 變更事件或排程；目前只保證 AI 執行修改任務時的工作流程，不假裝 Google 文件有自行執行程式的能力。

## 必須注意的負餘額待決議案例
「允許負數二次，不論數字多大」已列為需求，但『兩次』定義、重設期、回補/計費規則、技術數值範圍未定；當前 SQL 非負 CHECK 與 Gateway 限制 1..1,000,000。不可繞過 CHECK 或正式啟用透支，直到決議明確、完成隔離驗收。跨 App 同會員須原子計算透支次數；失敗／取消／逾時不得耗掉額外使用次數。

## 長期協作原則
發現比使用者原始想法更標準、更可靠、對其他 App 侵入更低或更安全的方案時，AI 必須主動提出具體替代選項與推薦原因，再據正式決議實作。
